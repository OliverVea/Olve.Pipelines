# M0 — Minimum Viable Pipeline

**Goal:** The Olve.Pipelines API can define and execute the CD pipeline for the Olve.Pipelines service itself.

**Litmus test pipeline:**

```
Production: [dotnet-build, docker-build]  (parallel)
    |
    v  ArtifactBundle
Processing:
    deploy-staging
    -> run-tests-against-staging
    -> deploy-prod
    -> release-api-clients              (sequential)
```

A user can, through API calls alone:

1. Create this pipeline with production and processing steps
2. Configure each step with image, script, and env vars
3. Store secrets (registry credentials, kubeconfig tokens)
4. Trigger production, which builds artifacts and automatically cascades through all processing steps
5. Observe job status and read logs to diagnose failures
6. Re-trigger production to get a full pipeline run

## What exists today

- Pipeline, ProductionStep, ProcessingStep full CRUD with cascade deletes
- StepConfiguration (image, script, env) attachment for both step types
- Job entity with state machine (Scheduled, InProgress, Done, Obsolete, Cancelled, Failed)
- Job supersession (latest-wins per pipeline+step key)
- Job cancellation on pipeline delete
- ArtifactBundle entity with metadata persistence to S3
- K8s Secret management via API
- K8s client with job manifest generation, status polling, log retrieval
- KubernetesJobExecutor runs ProductionJobs and ProcessingJobs as real K8s Jobs with polling and S3 bundle flow
- DownstreamTriggerService cascades production → processing steps automatically
- Job log endpoint serving S3-persisted runner logs (captured on success and failure)
- S3 persistence for configuration snapshots and bundle metadata
- Integration tests for CRUD, trigger validation, persistence across restart

## M0 Requirements

### M0.1 — Job Execution

**Currently:** `JobRunner` is a polling `BackgroundService` that picks up scheduled jobs via `JobQueueService` and delegates to `IJobExecutor`. Supports `MaxConcurrentJobs`, `Failed` status, and result-setting for both job types. The active executor is `NoOpJobExecutor` (blocks until `Finish()` is called; used for testing). No real K8s executor yet.

**Required:**

- [x] **M0.1a** ProductionJob execution: for each production step, create a K8s Job with the step's configuration (image, script, env), pipeline secrets, and an output S3 key. Run all production steps in parallel.
- [x] **M0.1b** ProcessingJob execution: create a K8s Job with the processing step's configuration, pipeline secrets, input bundle S3 key, and output S3 key.
- [x] **M0.1c** Job status polling: poll K8s Job status and update the domain Job entity (`InProgress` while running, `Done` on success, transition to failed state on failure).
- [x] **M0.1d** Job failure handling: when a K8s Job fails, the domain Job must reflect failure. Failed jobs must not trigger downstream steps.

**Acceptance criteria:**
- Triggering production creates real K8s Jobs that execute containers.
- Job status in the API reflects actual K8s Job status.
- A script that exits non-zero results in a failed job.

### M0.2 — Artifact Bundle Content

**Currently:** ArtifactBundles have metadata but no actual file content flows between steps.

**Required:**

- [x] **M0.2a** Production steps write output to a well-known path; the JobRunner collects outputs from all production steps into a single ArtifactBundle zip and uploads to S3.
- [x] **M0.2b** Processing steps receive the ArtifactBundle: the input bundle S3 key is injected as an environment variable, and the bundle is available to the script.
- [x] **M0.2c** ArtifactBundle status is updated to `Completed` when all production steps succeed, or `Failed` if any production step fails.

**Acceptance criteria:**
- A production step that writes files to its output directory produces a downloadable artifact bundle in S3.
- A processing step can access files produced by production steps.

### M0.3 — Automatic Downstream Triggering

**Currently:** Production completion does not trigger processing steps. Each step must be triggered manually.

**Required:**

- [x] **M0.3a** When a ProductionJob completes successfully and the ArtifactBundle is `Completed`, automatically create a ProcessingJob for the first processing step (by order).
- [x] **M0.3b** When a ProcessingJob completes successfully, automatically create a ProcessingJob for the next processing step (by order). If it was the last step, the pipeline run is complete.
- [x] **M0.3c** When a ProductionJob or ProcessingJob fails, do not trigger downstream steps.

**Acceptance criteria:**
- Triggering production on the litmus test pipeline results in: production -> deploy-staging -> run-tests -> deploy-prod -> release-clients, with no manual intervention.
- If deploy-staging fails, subsequent steps are never scheduled.

### M0.4 — Job Log Endpoint

**Currently:** Logs are persisted to S3 at `bundles/{pid}/{bid}/logs/{jid}.log` on job completion (success or failure) and served via `GET /api/jobs/{id}/logs`.

**Required:**

- [x] **M0.4a** `GET /api/jobs/{id}/logs` — returns the runner container logs for the K8s Job associated with the given domain Job.
- [x] **M0.4b** Returns `Result.Failure` (400) when logs are not yet persisted (job hasn't completed) or the job id is unknown.
- [x] **M0.4c** Logs are captured from the runner container specifically (not the s3-upload main container).

**Acceptance criteria:**
- After a job completes (success or failure), a user can retrieve the script output via the API.

### M0.5 — Integration Tests

**Currently:** Tests cover CRUD and trigger validation but not actual execution or cascading.

**Required:**

- [x] **M0.5a** End-to-end test: create pipeline with production + processing steps, trigger, verify jobs cascade through all steps and reach Done.
- [x] **M0.5b** Failure test: production step with a failing script results in a failed job, no downstream processing triggered.
- [x] **M0.5c** Artifact flow test: production step produces files, processing step can access them.
- [x] **M0.5d** Log retrieval test: after job completion, logs endpoint returns script output.

**Acceptance criteria:**
- All tests pass in CI with Testcontainers (Docker + MinIO + K8s or mock K8s).

### M0.6 — Configuration Persistence Reliability

**Currently:** `ConfigurationPersistenceService.StartingAsync` crashes with `NullReferenceException` at line 121 (`foreach (var s in snapshot.ProductionSteps)`) when an older/partial snapshot exists in S3. Exception is caught but the pipeline config is silently lost — every deploy wipes all configured pipelines. Observed in beta during manual testing of M0.4.

**Required:**

- [x] **M0.6a** `LoadSnapshot` tolerates null arrays (`snapshot.Pipelines`, `.ProductionSteps`, `.ProcessingSteps`) by treating them as empty. Null-coalesce at the foreach sites or on deserialization.
- [x] **M0.6b** Save immediately after load on startup (in addition to `StoppingAsync`) so schema-migrated data is persisted right away and ungraceful shutdowns lose at most changes since startup.
- [x] **M0.6c** Integration test: save snapshot, write an older-shaped snapshot to the fake S3 store with nulls, verify app starts without throwing and loads whatever valid data is present.

**Acceptance criteria:**
- Deploying a new version of Olve.Pipelines to K8s does not wipe existing pipeline configuration.
- An ungraceful termination (kill -9, OOM, node eviction) loses at most one save interval of config changes.

### M0.7 — Deployable Container Image

**Currently:** No `Dockerfile` exists. Olve.Pipelines can't be containerized and therefore can't be deployed via its own pipeline. A helm chart exists at `helm/` but has no image to reference.

**Required:**

- [x] **M0.7a** `Dockerfile` at repo root that produces a self-contained image of the API (AOT-published, minimal runtime base).
- [x] **M0.7b** Image runs as non-root, listens on port from config (defaults to 5000), healthy startup against beta env.
- [x] **M0.7c** Helm chart `helm/values.yaml` references this image (tag placeholder OK — pipeline substitutes on deploy).

**Acceptance criteria:**
- `docker build -t olve-pipelines:local . && docker run --rm -p 5000:5000 olve-pipelines:local` starts the API.
- The built image can be pushed to the beta registry and deployed via the helm chart.

## Out of scope for M0

- Typed step templates (DotNetBuild, HelmDeploy, etc.) — manual scripts are sufficient
- GitHub webhooks / source polling — manual trigger is sufficient
- Signal protocol beyond pass/fail
- Frontend / UI
- TypeScript client regeneration
- Bundle download endpoint for users (only needs to work between steps)
- Multi-cluster support
- RBAC / per-pipeline permissions
