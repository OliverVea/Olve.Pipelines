# M0 — Minimum Viable Pipeline

**Goal:** The Olve.Pipelines API can define and execute the CD pipeline for the Olve.Pipelines service itself.

**Litmus test pipeline:**

```
Production: [dotnet-build, docker-build]  (parallel)
    |
    v  ArtifactBundle
Processing:
    deploy-staging
    -> run-tests-against-staging
    -> deploy-prod
    -> release-api-clients              (sequential)
```

A user can, through API calls alone:

1. Create this pipeline with production and processing steps
2. Configure each step with image, script, and env vars
3. Store secrets (registry credentials, kubeconfig tokens)
4. Trigger production, which builds artifacts and automatically cascades through all processing steps
5. Observe job status and read logs to diagnose failures
6. Re-trigger production to get a full pipeline run

## What exists today

- Pipeline, ProductionStep, ProcessingStep full CRUD with cascade deletes
- StepConfiguration (image, script, env) attachment for both step types
- Job entity with state machine (Scheduled, InProgress, Done, Obsolete, Cancelled)
- Job supersession (latest-wins per pipeline+step key)
- Job cancellation on pipeline delete
- ArtifactBundle entity with metadata persistence to S3
- K8s Secret management via API
- K8s client with job manifest generation, status polling, log retrieval
- S3 persistence for configuration snapshots and bundle metadata
- Integration tests for CRUD, trigger validation, persistence across restart

## M0 Requirements

### M0.1 — Job Execution

**Currently:** `JobRunner` is a no-op. Jobs go `Scheduled -> InProgress -> Done` instantly without running anything.

**Required:**

- [ ] **M0.1a** ProductionJob execution: for each production step, create a K8s Job with the step's configuration (image, script, env), pipeline secrets, and an output S3 key. Run all production steps in parallel.
- [ ] **M0.1b** ProcessingJob execution: create a K8s Job with the processing step's configuration, pipeline secrets, input bundle S3 key, and output S3 key.
- [ ] **M0.1c** Job status polling: poll K8s Job status and update the domain Job entity (`InProgress` while running, `Done` on success, transition to failed state on failure).
- [ ] **M0.1d** Job failure handling: when a K8s Job fails, the domain Job must reflect failure. Failed jobs must not trigger downstream steps.

**Acceptance criteria:**
- Triggering production creates real K8s Jobs that execute containers.
- Job status in the API reflects actual K8s Job status.
- A script that exits non-zero results in a failed job.

### M0.2 — Artifact Bundle Content

**Currently:** ArtifactBundles have metadata but no actual file content flows between steps.

**Required:**

- [ ] **M0.2a** Production steps write output to a well-known path; the JobRunner collects outputs from all production steps into a single ArtifactBundle zip and uploads to S3.
- [ ] **M0.2b** Processing steps receive the ArtifactBundle: the input bundle S3 key is injected as an environment variable, and the bundle is available to the script.
- [ ] **M0.2c** ArtifactBundle status is updated to `Completed` when all production steps succeed, or `Failed` if any production step fails.

**Acceptance criteria:**
- A production step that writes files to its output directory produces a downloadable artifact bundle in S3.
- A processing step can access files produced by production steps.

### M0.3 — Automatic Downstream Triggering

**Currently:** Production completion does not trigger processing steps. Each step must be triggered manually.

**Required:**

- [ ] **M0.3a** When a ProductionJob completes successfully and the ArtifactBundle is `Completed`, automatically create a ProcessingJob for the first processing step (by order).
- [ ] **M0.3b** When a ProcessingJob completes successfully, automatically create a ProcessingJob for the next processing step (by order). If it was the last step, the pipeline run is complete.
- [ ] **M0.3c** When a ProductionJob or ProcessingJob fails, do not trigger downstream steps.

**Acceptance criteria:**
- Triggering production on the litmus test pipeline results in: production -> deploy-staging -> run-tests -> deploy-prod -> release-clients, with no manual intervention.
- If deploy-staging fails, subsequent steps are never scheduled.

### M0.4 — Job Log Endpoint

**Currently:** `KubernetesClient.GetPodLogsAsync` exists but is not exposed via the API.

**Required:**

- [ ] **M0.5a** `GET /api/jobs/{id}/logs` — returns the pod logs for the K8s Job associated with the given domain Job.
- [ ] **M0.5b** Returns 422 if the job has not started yet (no pod exists).

**Acceptance criteria:**
- After a job completes (success or failure), a user can retrieve the script output via the API.

### M0.5 — Integration Tests

**Currently:** Tests cover CRUD and trigger validation but not actual execution or cascading.

**Required:**

- [ ] **M0.5a** End-to-end test: create pipeline with production + processing steps, trigger, verify jobs cascade through all steps and reach Done.
- [ ] **M0.5b** Failure test: production step with a failing script results in a failed job, no downstream processing triggered.
- [ ] **M0.5c** Artifact flow test: production step produces files, processing step can access them.
- [ ] **M0.5d** Log retrieval test: after job completion, logs endpoint returns script output.

**Acceptance criteria:**
- All tests pass in CI with Testcontainers (Docker + MinIO + K8s or mock K8s).

## Out of scope for M0

- Typed step templates (DotNetBuild, HelmDeploy, etc.) — manual scripts are sufficient
- GitHub webhooks / source polling — manual trigger is sufficient
- Signal protocol beyond pass/fail
- Frontend / UI
- TypeScript client regeneration
- Bundle download endpoint for users (only needs to work between steps)
- Multi-cluster support
- RBAC / per-pipeline permissions
