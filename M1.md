# M1 — Operational Reliability & UI

**Goal:** Make Olve.Pipelines operationally sustainable and add a basic web UI for pipeline management.

## M1.1 — Kubernetes Job Cleanup

**Currently:** Completed and failed K8s Jobs accumulate forever in the `olve-runners` namespace. `KubernetesClient.DeleteJobAsync` exists but is never called. No TTL is set on job manifests.

**Required:**

- [ ] **M1.1a** Delete K8s Jobs after completion: call `DeleteJobAsync` in `KubernetesJobExecutor.CreatePollAndCleanupAsync` after a job reaches Done or Failed status.
- [ ] **M1.1b** Set `ttlSecondsAfterFinished` on K8s Job manifests as a safety net (e.g. 1 hour) in case the app crashes before cleaning up.
- [ ] **M1.1c** Cleanup of orphaned jobs: background task that periodically scans for K8s Jobs in the runner namespace that have no matching domain Job (or whose domain Job is already terminal) and deletes them.

**Acceptance criteria:**
- After a pipeline run completes, no stale K8s Jobs remain in the runner namespace.
- Orphaned jobs from crashed runs are cleaned up within a configurable interval.

## M1.2 — Web UI

**Currently:** All pipeline management is API-only. No visual interface for creating pipelines, viewing jobs, or reading logs.

**Required:**

- [ ] **M1.2a** Pipeline list view: shows all pipelines with their steps.
- [ ] **M1.2b** Pipeline detail view: shows production and processing steps with their configuration, secrets (names only), and triggers.
- [ ] **M1.2c** Job list view: shows all jobs with status, timestamps, and pipeline association. Auto-refreshes or polls.
- [ ] **M1.2d** Job log view: displays job logs with formatting.
- [ ] **M1.2e** Trigger button: manually trigger a pipeline's production from the UI.
- [ ] **M1.2f** Pipeline CRUD: create/edit/delete pipelines and steps from the UI.

**Acceptance criteria:**
- A user can create a pipeline, configure steps, trigger a run, and view logs entirely through the web UI.
- The UI is served by the same ASP.NET app (no separate frontend deployment).

## M1.3 — Client Generation

**Currently:** OpenAPI spec `api.json` is generated on build. C# client is generated via Refitter (.refitter file), TypeScript client via Kiota. Both are manual processes.

**Required:**

- [ ] **M1.3a** Generated TypeScript client: publish as npm package or include in repo, regenerated from `api.json`.
- [ ] **M1.3b** Generated C# API client: publish as NuGet package or include in repo, regenerated from `api.json` via Refitter.
- [ ] **M1.3c** CLI client: command-line tool wrapping the C# API client for scripting pipeline operations (create, configure, trigger, status, logs).
- [ ] **M1.3d** Automated regeneration: pipeline step or build target that regenerates clients when `api.json` changes.

**Acceptance criteria:**
- TS and C# clients are available and usable against a running Olve.Pipelines instance.
- CLI can perform basic pipeline operations (list, trigger, logs).

## M1.4 — Build Speed

**Currently:** Full pipeline run takes ~5-7 minutes (3-5 min Kaniko build + 1-2 min deploy). The deploy step installs openssh-client from scratch every run.

**Ideas for improvement:**

- [ ] **M1.4a** Kaniko layer caching: use `--cache=true` with a cache repo to avoid rebuilding unchanged layers.
- [ ] **M1.4b** Pre-built deploy image: replace `alpine:latest` + `apk add openssh-client` with a custom image that already has SSH installed.
- [ ] **M1.4c** Skip redundant builds: compare git SHA or source hash, skip production if code hasn't changed since last successful build.

**Acceptance criteria:**
- Incremental builds (no source changes) complete significantly faster than clean builds.
- Deploy step starts executing within seconds (no package installation).

## Out of scope for M1

- Pipeline configuration persistence to a database (in-memory + S3 snapshots is sufficient)
- Multi-cluster support
- RBAC / per-pipeline permissions
- GitHub webhook integration (manual trigger + webhook trigger is sufficient)
