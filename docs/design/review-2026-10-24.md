## Strengths

1. Contract rigour: the schema, server re-validation, and api.json/Kiota drift checks.
2. A typed SDK with compile-time wiring errors.
3. The scheduler: stateless, latest-wins per step, supersede instead of race, reattach after a
   self-redeploy.
4. Fast, readable scenario tests (877 in about 10 s).
5. A deliberate agent surface: `pl wait` exit codes, `/llms.txt`, and a skill that matches the code.

## Risks

1. No authorization layer and no secret masking in logs.
2. Not self-hostable by others yet: no public server image, homelab-coupled values.
3. Every push goes to prod, and the SDK/frontend checks run after prod.
4. No app-level rollback or approval gates.
5. Doc and agent-surface drift across the three repos.

## Recommended improvements, in order

1. **Gate deploys on the SDK check (`bun run check`) and the frontend build/lint, in the stage with
   `build` and `test`, before `deploy-beta`.** Cheap; do this first.
2. Roles (admin / operator / viewer) and masking of declared secret values in logs.
3. Publish the server image; make `values-minimal` free of homelab hosts; verify `pl bootstrap` on a
   bare k3s.
4. Environments (a record of what is deployed where) with redeploy-previous rollback; an approval
   gating step.
5. A drift pass over README, AGENTS.md and the skill; behavioural agent evals (does the agent use
   `pl wait`, ask before prod, avoid tokens) run as part of the release.

## Decided: verify early, build once, promote

Follow-up to recommendation 1. Each component is **built and verified once**, in its own parallel
step; the artifacts are **published as prereleases** in a stage of their own, after every check has
passed (steps in a stage run in parallel, so a prerelease must never share a stage with a check);
later stages **promote the same artifacts** instead of rebuilding them. Deploys always use digests.

Pipeline shape (as built in `.pipelines/pipeline.ts`, 2026-10-24):
1. `source`
2. In parallel, build and verify only; publish nothing:
   - `build-server`: the server image (Dockerfile as-is: it builds and type-checks the frontend),
     pushed under the run's version tag (a throwaway per-run tag, not a published one)
   - `build-harness`: the step pods' init image, under its content tag (`src-<hash>`)
   - `test`: dotnet test + api.json/Kiota drift
   - `frontend-lint`: `npm run lint` + `npm run format:check`
   - `build-sdk`: `bun run check` (tsc, compile-fail, bun test) + `bun pm pack` → `.tgz`
   - `build-cli`: `pl` for Linux and Windows
3. Publish prereleases, from exactly those artifacts:
   - `publish-images`: tag both digests `next` (registry API, no rebuild)
   - `publish-sdk`: `bun publish <the packed .tgz> --tag next`
   - `publish-cli`: the release the instance serves at `/download` (once the run is promoted)
4. `deploy-beta`, by digest
5. `beta-test`
6. `deploy-prod`, the same digests
7. `promote`: `latest` on the image digests, `npm dist-tag add <pkg>@<v> <release tag>`

| Artifact | Prerelease (stage 3) | Promote (after prod) |
|---|---|---|
| SDK (npm) | `--tag next` of the packed tarball | dist-tag moved to the same version (`beta` while the SDK is a 2.0 beta) |
| Server / harness images | `next` on the run's digests | `latest` on the same digests |
| `pl` CLI | `publish-cli` output | `/download` serves it (`Distribution:CliPromotedBy=promote`) |

Everything is gated by the pipeline's `publish` config: a target that is off is skipped. Versions
stay final semver; the tag says how far an artifact has been promoted.
